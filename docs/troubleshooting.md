## 1. 슬롯 정원 동시성

**상황** — 시간대별로 정원(예: 10팀)이 있는 예약 기능을 만들고 있었다.

**문제** — 예약 생성은 "현재 예약 수를 조회 → 정원 미만이면 예약 생성" 순서였다. 두 요청이 거의 동시에 들어오면 둘 다 조회 시점에 9팀을 보고 둘 다 통과해서 11팀이 된다. 단일 사용자로 테스트할 때는 절대 재현되지 않는다.

**원인 분석** — 검사와 갱신 사이에 간격이 있는 전형적인 TOCTOU다. 트랜잭션으로 감싸도 기본 격리 수준에서는 두 트랜잭션이 같은 값을 읽는 것을 막지 못한다. 애플리케이션이 아니라 **DB가 검사와 증가를 한 번에 처리**해야 한다.

**해결** — 카운터 증가 조건을 `UPDATE` 문 자체에 넣고, 갱신된 행 수로 성공 여부를 판단한다. ([db-reservation-repository.ts:153](../src/lib/server/db-reservation-repository.ts#L153))

```sql
UPDATE reservation_slots
SET reserved_count = reserved_count + 1
WHERE gym_id = $1 AND sport = $2 AND "date" = $3 AND "time" = $4
  AND is_closed = false
  AND reserved_count < capacity
```

`updatedCount !== 1`이면 `ReservationSlotFullError`를 던져 트랜잭션 전체를 되돌린다. 구현 중 두 가지를 더 만났다.

- Prisma의 `updateMany`는 **컬럼 대 컬럼 비교**(`reserved_count < capacity`)를 지원하지 않는다. 그래서 raw SQL이 필요했다.
- `date`와 `time`은 Postgres 예약어라 `"date"`처럼 큰따옴표로 escape해야 한다.

**결과/배운 점** — k6로 정원 10팀 슬롯에 서로 다른 사용자 200명을 동시에 붙여 검증한다. 기대값은 성공 10건 / 마감 190건이다. 이때 **HTTP 응답만 세면 안 된다**는 걸 배웠다. 응답이 200이어도 카운터만 오르고 예약 행이 없을 수 있어서, `slot.mjs verify`가 DB 상태로 네 가지 불변식을 따로 확인한다.

| 불변식 | 확인 내용 |
|---|---|
| `reservedCount <= capacity` | 정원 초과 없음 |
| `actualReservations == reservedCount` | 카운터만 오르는 상황 배제 |
| `uniqueUsers == 예약 수` | 한 사람이 두 자리 차지 배제 |
| `uniqueActiveKeys == 예약 수` | 중복 예약 배제 |

동시성 버그는 "테스트를 통과했다"가 아니라 "무엇을 불변식으로 정의하고 그것을 DB에서 확인했다"로만 증명된다.

## 2. 중복 예약 방지

**상황** — 같은 사용자가 같은 체육관·종목·날짜·시간에 예약을 두 번 만들 수 없어야 했다.

**문제** — 1번과 같은 종류의 경합이다. "기존 활성 예약이 있는지 조회 → 없으면 생성"은 더블 클릭이나 동시 요청에서 뚫린다.

**원인 분석** — 정합성의 최종 방어선을 애플리케이션 코드에 두면 안 된다. **DB의 UNIQUE 제약**이 유일하게 신뢰할 수 있는 지점이다.

**해결** — `(userId, gymId, sport, date, time)`을 인코딩한 `activeKey`를 만들고, `reservation_locks.activeKey`에 UNIQUE를 건다. 예약 생성 트랜잭션은 슬롯 카운터 증가 · 예약 생성 · lock 생성을 함께 수행하고, lock INSERT가 UNIQUE 충돌(P2002)을 내면 트랜잭션 전체가 롤백된다. ([db-reservation-repository.ts:1004](../src/lib/server/db-reservation-repository.ts#L1004))

취소 시에는 lock을 제거하고 슬롯 카운터를 감소시켜, 같은 자리를 다시 예약할 수 있게 한다.

**결과/배운 점** — 애플리케이션의 사전 조회는 **사용자에게 친절한 에러 메시지를 주기 위한 것**이고, 정합성은 DB 제약이 책임진다. 두 계층의 역할을 분리해서 생각하게 됐다.

## 3. 챗봇 세션 격리

> 커밋 [`5ba1c71`](https://github.com/nakyung123/gym-reservation-web/commit/5ba1c71)

**상황** — FAQ 안내봇에 "내 예약 조회" 도구를 붙인 직후였다. 서버는 로그인한 사용자의 uid로만 예약을 조회하도록 설계했고, 도구는 uid를 파라미터로 **받지 않는다**(모델이 남의 uid를 지어낼 수 없게 하려는 의도).

**문제** — 배포 후 확인하다가 발견했다. 로그아웃한 뒤 "내 예약 언제야?"를 다시 물으면 **이전 사용자의 예약 내역이 그대로 나왔다.** 새로고침하면 정상이었다.

**원인 분석** — 처음에는 서버의 uid 스코프가 뚫렸다고 의심했지만, 서버는 정상이었다. 유출 경로는 클라이언트였다.

1. FAQ 위젯은 루트 레이아웃에 상주해서 로그아웃으로 **언마운트되지 않는다.**
2. 서버는 stateless라 `send()`가 매 요청마다 **대화 이력 전체**를 다시 보낸다.
3. 이전 답변에 이미 예약 내역이 텍스트로 들어 있다. 모델은 도구를 호출할 필요 없이 그 내용을 그대로 반복한다.

새로고침하면 정상이었던 이유도 같다. 새로고침은 위젯을 언마운트해서 이력을 날린다.

공용 PC라면 로그아웃한 다음 사람이 위젯을 열었을 때 이전 사용자의 예약이 보이는 상황이라 그냥 둘 수 없었다.

**해결** — `useSyncExternalStore`로 Firebase 인증 상태를 구독하고, **확정된 로그인 주체가 바뀌면**(로그인→로그아웃, 계정 전환) 대화·상태·오류를 비운다. ([use-faq-chat.ts](../src/hooks/use-faq-chat.ts))

핵심은 "확정된"이다. 초기화 중(`not-ready`)에는 판단하지 않는다. 그러지 않으면 첫 로드에서 인증 상태가 잡히기 전에 헛되이 대화를 지운다.

**결과/배운 점** — 회귀 테스트 2건(로그아웃 / 계정 전환)을 추가했고, 초기화 로직을 제거하면 두 건 모두 실패하는 것까지 확인했다.

배운 점이 두 가지다. 첫째, **서버 권한 검사가 옳아도 클라이언트가 상태를 들고 있으면 유출된다.** 권한 경계를 서버에만 그리면 안 된다. 둘째, LLM 대화 이력은 그 자체가 **캐시**다. 이력에 한 번 들어간 민감 정보는 도구 호출 없이도 재생된다.

## 4. 예약 폼 18N 비교 제거

> 커밋 [`a406231`](https://github.com/nakyung123/gym-reservation-web/commit/a406231)

**상황** — 예약 폼은 시간대 18개를 한 화면에 보여주고, 각 시간대마다 "이미 예약한 시간인지"를 표시한다.

**문제** — 시간대 18개 각각에 `getReservationTimeState`를 호출하고, 그 안의 `findActiveDuplicate`가 매번 사용자의 **전체 예약 목록을 처음부터 훑었다.** 누적 예약이 2,000건인 사용자라면 폼을 한 번 재계산할 때마다 36,000번을 비교한다.

**원인 분석** — 중복 판정 조건은 `userId · gymId · sport · date · time`과 `status = "reserved"`의 조합인데, 이 중 **시간대별로 달라지는 건 `time` 하나뿐이다.** 나머지 조건은 18번 반복할 이유가 없다.

**해결** — `time`을 제외한 조건으로 후보를 **한 번만** 좁힌 뒤, 좁혀진 목록으로 18번 판정한다. 좁히는 함수(`filterActiveDuplicateCandidates`)를 판정 함수와 **같은 파일**(`reservation-rules.ts`)에 뒀다. 두 규칙이 서로 다른 파일에 있으면 나중에 조건이 갈라지기 때문이다.

비교 횟수가 `18N`에서 `N + 18 × (소수의 후보)`로 줄었다.

**결과/배운 점** — 최적화가 동작을 바꾸지 않았음을 테스트로 잠갔다. **좁힌 목록과 전체 목록의 `validateReservationDraft` 결과가 모든 시간대에서 같아야 한다**는 동치성 테스트다. 이 테스트가 실제로 유효한지 확인하려고 좁히기 함수가 빈 배열을 반환하도록 일부러 망가뜨려 봤고, 3건이 실패하는 것을 확인했다.

성능 개선 PR에서 제일 중요한 건 빨라진 수치가 아니라 **결과가 같다는 증명**이라는 걸 배웠다.

## 5. 인덱스 최적화와 측정의 함정

> 커밋 [`5bbf144`](https://github.com/nakyung123/gym-reservation-web/commit/5bbf144)

**상황** — 관리자 예약 목록, 일자 개요, 매출 집계 화면을 만든 뒤 조회 성능을 점검했다.

**문제** — `reservations` 테이블의 인덱스가 `[userId, createdAt]` 하나뿐이었다. 그런데 관리자 쿼리들은 **`userId` 없이 `date`나 `gymId`로 조회**한다. 선두 컬럼이 맞지 않아 전부 풀스캔이었다. `reservation_slots`도 `[gymId, date]`라 `date` 단독 조회에 인덱스를 타지 못했다.

**해결** — 조회 패턴에 맞는 인덱스 3개를 추가했다.

| 인덱스 | 대상 쿼리 |
|---|---|
| `idx_res_date_status` | 관리자 예약 목록 · 일자 개요 · 매출 집계 |
| `idx_res_gym_date` | 체육관별 필터(`gymId` 단독 / `gymId + date`) |
| `idx_res_slots_date` | 슬롯 일자 조회 |

`date`는 `VARCHAR(10)`의 `"YYYY-MM-DD"`라 사전식 정렬이 곧 시간순이고, 범위 조회도 같은 인덱스를 탄다.

`EXPLAIN`으로 대상 쿼리 6건이 모두 인덱스에 매칭되는 것과, 기존 `idx_res_user_created`에 회귀가 없는 것을 확인했다.

**여기서 두 번 배웠다.**

**(1) 데이터가 적으면 인덱스는 사용되지 않는다.** dev 규모(1,328행)에서는 플래너가 여전히 Seq Scan을 골랐다. 이건 버그가 아니라 정상 동작이다. 전체의 상당 비율을 읽어야 하는 쿼리라면 순차 스캔이 실제로 더 빠르다. 그래서 부하 테스트에서는 예약을 12만건까지 늘리고, 날짜를 2년(730일)에 분산시켜 **한 달 조회가 전체의 약 4%**가 되게 만들었다. 인덱스가 유리해지는 선택도를 인위적으로 만들어 준 것이다.

**(2) HTTP 응답시간만 재면 잘못된 결론에 도달한다.** 관리자 엔드포인트는 요청마다 `verifyIdToken(idToken, true)`로 Firebase에 **revoked 토큰 검사 네트워크 왕복**을 한다. 권한 회수를 즉시 반영하기 위한 의도적 선택이다([admin-auth.ts:43](../src/lib/server/admin-auth.ts#L43)). 이 왕복이 응답시간의 대부분을 차지해서, DB 쿼리가 아무리 빨라져도 **HTTP 개선폭은 작게 나온다.**

그래서 부하 테스트를 두 계층으로 나눠서 측정한다. `admin-read.js`가 HTTP를 재고, `db-timing.mjs`가 `EXPLAIN ANALYZE`로 DB 계층만 따로 잰다. 두 숫자를 함께 봐야 "DB는 빨라졌지만 사용자 체감은 인증 비용에 묶여 있다"는 결론에 도달할 수 있다.

**측정 결과** — 예약 121,328행(k6 시딩 12만 + 기존), 로컬 프로덕션 빌드, VU 10 / 30초 기준.

DB 계층 (`EXPLAIN ANALYZE` 중앙값):

| 쿼리 | 인덱스 없음 | 인덱스 있음 | 배수 |
|---|---|---|---|
| 예약 목록 (`date`) | 14.67 ms (Seq Scan) | 0.26 ms (Index) | **약 56배** |
| 일자 개요 (`date + status`) | 15.51 ms (Seq Scan) | 0.05 ms (Index) | **약 310배** |
| 매출 집계 (월 범위 groupBy) | 24.13 ms (Seq Scan) | 2.55 ms (Index) | **약 9.5배** |
| 슬롯 개요 (`date`) | 0.01 ms (Seq Scan) | 0.01 ms (Seq Scan) | 변화 없음 |

HTTP 계층 (k6, 실패 0%):

| 지표 | 인덱스 없음 | 인덱스 있음 | 개선 |
|---|---|---|---|
| median | 298.32 ms | 267.36 ms | **약 10%** |
| avg | 308.64 ms | 278.61 ms | 약 10% |

**DB 계층은 최대 310배 빨라졌는데 사용자가 보는 HTTP는 10%만 빨라졌다.** 나머지 약 260ms가 Firebase revoked 토큰 검사 왕복이다.

슬롯 개요는 인덱스가 있어도 플래너가 Seq Scan을 골랐다. `reservation_slots`는 행이 적어 순차 스캔이 실제로 더 싸기 때문이고, 이것도 정상 동작이다.

**결과/배운 점** — 최적화보다 **어디를 재야 하는지 정하는 게 먼저**였다. 만약 HTTP만 쟀다면 "인덱스는 10%밖에 효과가 없다"고 잘못 결론 내리고, 진짜 병목이 인증 왕복이라는 사실도, 인덱스가 데이터 증가에 대비해 제대로 작동한다는 사실도 둘 다 놓쳤을 것이다.

거꾸로 DB 수치만 들고 "310배 개선했다"고 말하는 것도 정직하지 않다. 사용자가 체감하는 건 10%다. **두 숫자를 함께 제시하는 게 맞다.**

부수적으로, `admin-read.js`가 rate limit(IP당 60회/분)을 우회하려고 반복마다 다른 `X-Forwarded-For`를 보내는데, **이게 통한다는 것 자체가 `extractClientIp`가 XFF를 검증 없이 신뢰한다는 뜻**이라는 것도 이 과정에서 알게 됐다. Vercel 뒤에서는 플랫폼이 XFF를 세팅하므로 대체로 안전하지만, 앱에 직접 도달하는 경로가 생기면 rate limit이 무력화될 수 있는 알려진 한계로 남겨 뒀다.

## 6. AI 브리핑의 PII와 인젝션 경계

**상황** — 매일 운영 지표를 Slack으로 보내는 일일 리포트에, 숫자만이 아니라 자연어 해석·이상치·탈퇴 사유 테마를 붙이고 싶었다. 이 레이어를 Claude로 처리한다. ([ai-brief.ts](../src/lib/server/ai-brief.ts))

**문제** — 입력에 **탈퇴 사유 자유텍스트**가 들어간다. 사용자가 직접 쓴 문장이라 두 가지 위험이 있다.

1. 이름·전화번호·이메일이 섞여 들어갈 수 있다 (제3자 API로 나가는 개인정보)
2. 사용자가 쓴 문장이 **모델에게 지시처럼 읽힐 수 있다** (프롬프트 인젝션)

**해결** — 세 겹으로 막았다.

1. **전송 전 스크럽** — 이메일·전화번호 패턴을 정규식으로 마스킹한다. 자유텍스트라 완벽 탐지는 불가능하므로 보수적으로 넓게 가린다. 오탐(날짜가 가려지는 등)은 정보 손실일 뿐 누출이 아니라고 판단했다.
2. **시스템 프롬프트로 출력 제약** — 원문 인용과 PII 출력을 금지하고 테마로만 요약하게 강제한다.
3. **데이터/지시 경계 명시** — 탈퇴 텍스트는 '데이터'이지 '지시'가 아니라고 시스템 프롬프트에 못 박는다.

추가로 **best-effort 폴백**을 설계했다. API 키 미설정, API 실패, 스키마 검증 실패는 모두 `null`을 반환하고 호출측은 **숫자 리포트로 그대로 폴백한다.** AI 실패가 리포트 전체를 막지 않는다. 응답은 Zod 스키마 기반 구조화 출력으로 받아 형태를 보장하고, 프롬프트 비대화를 막기 위해 탈퇴 사유는 최대 50건까지만 보낸다(수집 계층의 `take` 상한과 같은 상수를 공유해 SSOT를 유지).

**결과/배운 점** — LLM을 파이프라인에 넣는 순간 **입력이 어디서 왔는지**가 보안 문제가 된다. 사용자 자유텍스트를 모델에 그대로 넘기는 것은 SQL에 문자열을 그대로 붙이는 것과 같은 종류의 실수다. 그리고 AI 기능은 **없어도 시스템이 돌아가게** 설계해야 한다는 것 — 부가 레이어가 핵심 기능의 가용성을 떨어뜨리면 안 된다.

## 7. LLM 비용 상한 설계

**상황** — FAQ 안내봇을 공개 배포에 붙였다. 저장소는 public이고 위젯은 **로그인 없이 누구나** 열 수 있다.

**문제** — 인증이 없으니 악의적이든 실수든 반복 호출하면 API 비용이 그대로 발생한다. 개인 포트폴리오라 요금이 무한정 나가면 안 된다.

**원인 분석** — 인증을 붙이면 간단하지만, 그러면 "누구나 써 볼 수 있는 데모"라는 목적이 사라진다. **rate limit이 유일하고 필수인 방어선**이 되는 구조다.

**해결** — 두 층으로 막았다.

**코드 안** — rate limit 3단을 걸고, 전부 통과해야 LLM을 호출한다. ([faq-chat/route.ts](../src/app/api/faq-chat/route.ts))

| 단계 | 한도 |
|---|---|
| IP당 분당 | 5회 |
| IP당 일일 | 8회 |
| **전역 일일** | **20회** |

전역 캡이 핵심이다. IP는 바꿀 수 있지만 전역 한도는 못 넘는다.

**fail-closed** 원칙도 함께 넣었다. rate limit 계산 자체가 실패하면(DB 장애, secret 부재) LLM을 호출하지 않고 503으로 응답한다. 비용 컨트롤을 우회할 수 있는 경로를 남기지 않기 위해서다.

**코드 밖** — Anthropic 콘솔의 지출 한도와 선불 크레딧을 설정했다. 코드에 버그가 있어도 넘을 수 없는 절대 천장이다.

**결과/배운 점** — 공개 저장소라 "키가 유출되면?"도 검토했다. 키는 코드에 없고 `.env*`는 gitignore 대상이라 저장소가 공개돼도 비용은 발생하지 않는다. 로컬에서도 키가 없으면 호출 자체가 되지 않는다.

배운 점은 **AI 기능의 비용은 기능 요구사항이 아니라 보안 요구사항으로 다뤄야 한다**는 것이다. rate limit을 "남용 방지"가 아니라 "지출 상한"으로 설계하면 필요한 한도가 완전히 달라진다. 그리고 코드 안의 방어(우회 가능)와 코드 밖의 방어(우회 불가)를 **둘 다** 두는 게 맞다.
