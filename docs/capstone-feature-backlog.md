# 캡스톤 기능 확장 백로그

이 문서는 대학 캡스톤에서 기획했던 공공체육관 예약 앱 아이디어를 웹 MVP
이후 단계로 확장하기 위한 후보 목록입니다. 실제 캡스톤 구현 기능은 자료를
다시 확인하면서 추가하고, 현재 웹 프로젝트에서는 작동하는 MVP 기준점을 먼저
유지합니다.

## 진행 원칙

- 현재 MVP 흐름인 목록, 상세, 예약, 내 예약, 취소를 깨뜨리지 않습니다.
- 로그인, 관리자, 실제 운영 데이터처럼 의존성이 큰 기능은 별도 단계로
분리합니다.
- 기능을 붙일 때마다 Firestore 모델, 보안 규칙, 화면 상태를 함께 갱신합니다.
- 실제 시설 예약처럼 보일 수 있는 문구는 피하고, MVP/포트폴리오 성격을
명확히 유지합니다.

## 0단계 - MVP 마감

| 기능 | 상태 | 메모 |
| --- | --- | --- |
| 서울 공공체육시설 샘플 데이터 | 완료 | Firestore `gyms` seed와 mock JSON 기준을 맞춤 |
| 실제 예약 아님 안내 | 완료 | 전역 배너와 상세 화면에 표시 |
| 옛 체육관 예약 안전 표시 | 완료 | 현재 시설 목록에서 제외된 예약을 명시적으로 안내 |
| 최소 QA | 예정 | `http://localhost:3000` 기준 주요 흐름 확인 |
| GitHub push | 보류 | 사용자 승인 후 진행 |

## 1단계 - 사용자 탐색 개선

| 기능 | 우선순위 | 의존성 | 메모 |
| --- | --- | --- | --- |
| 지도/위치 기반 탐색 | 높음 | 지도 API 결정 | 서울 지역 MVP와 잘 맞는 확장 |
| 즐겨찾기 | 높음 | 로그인 정책 또는 로컬 저장 정책 | 로그인 전에는 localStorage 후보, 로그인 후 Firestore 후보 |
| 최근 본 시설 | 중간 | 저장 위치 결정 | 예약 전 재방문 흐름 개선 |
| 필터 확장 | 중간 | 데이터 필드 확장 | 지역구, 종목 외 운영 요일, 가격, 시설 유형 |
| 시설 비교 | 낮음 | UI 추가 | 가격, 종목, 운영시간 비교 |

## 2단계 - 계정과 개인화

| 기능 | 우선순위 | 의존성 | 메모 |
| --- | --- | --- | --- |
| 카카오 로그인 | 높음 | Firebase Auth 연동 방식 검토 | MVP 이후 우선 검토 |
| 네이버 로그인 | 중간 | custom auth 서버 필요 여부 검토 | Firebase 기본 provider가 아니므로 별도 설계 필요 |
| 익명 예약 이전 | 높음 | 로그인 정책 결정 | 기존 익명 예약을 로그인 계정으로 넘길지 결정 |
| 마이페이지 | 중간 | 계정 모델 | 예약 내역, 즐겨찾기, 사용자 정보 |
| 알림 설정 | 낮음 | 알림 채널 결정 | 이메일, 캘린더, 브라우저 알림 후보 |

## 3단계 - 예약 현실성 강화

| 기능 | 우선순위 | 의존성 | 메모 |
| --- | --- | --- | --- |
| 시간대별 잔여 수량 | 높음 | 운영 데이터 모델 | 현재는 중복 예약 방지만 구현 |
| 휴관일/운영시간 관리 | 높음 | 관리자 또는 seed 데이터 확장 | 실제 예약 가능성 표현에 필요 |
| 예약 상세 화면 | 중간 | 라우트 추가 | 예약번호별 상세, 취소 상태, 입장권 |
| 캘린더 저장 | 중간 | 클라이언트 기능 | 포트폴리오 기능으로 구현 부담 낮음 |
| QR 값 검증 흐름 | 낮음 | 관리자/현장 확인 화면 | 실제 입장권처럼 보이지 않도록 문구 주의 |

## 4단계 - 관리자 기능

| 기능 | 우선순위 | 의존성 | 메모 |
| --- | --- | --- | --- |
| 시설 관리 | 중간 | 관리자 권한 모델 | 이름, 주소, 종목, 운영시간 관리 |
| 예약 관리 | 중간 | 보안 규칙 확장 | 사용자 예약 조회와 상태 변경 |
| 휴관일 관리 | 중간 | 시설별 일정 모델 | 예약 가능 시간 계산과 연결 |
| 공지 관리 | 낮음 | 데이터 모델 | 시설별 안내 문구 |
